## 2025-03-20 - [Defense in Depth] Input Validation at Lowest Architectural Layer
**Vulnerability:** Shell commands (e.g., `lsof`, `netstat`, `kill`, `taskkill`) were constructed using parameters (`port`, `pid`, `protocol`) that were assumed to be validated by the top-level APIs (`index.ts`). If internal utility functions or future API changes bypass the top-level validation, malicious or malformed inputs could reach the platform-specific execution layers (`linux.ts`, `macos.ts`, `windows.ts`), potentially leading to command injection or unexpected behavior, even when using `child_process.spawn` with argument arrays.
**Learning:** Defense-in-depth requires that security controls (like input validation) be enforced as close to the sensitive operation as possible. Relying solely on validation at the entry point of a library is insufficient, as internal calls or future refactoring might bypass these checks.
**Prevention:** Always re-validate and normalize all external inputs (e.g., ports, PIDs, protocols) at the lowest platform architectural layer (immediately before they are interpolated into shell commands), using established validators (`validatePort`, `validatePID`, `normalizeProtocol`).
